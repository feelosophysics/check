🌟 Mini Git이란 무엇인가?

Git의 핵심은 복잡한 파일 저장이 아니라 커밋 간의 부모-자식 관계를 표현하는 그래프(DAG)와 이를 다루는 탐색 및 정렬 알고리즘입니다.

[1]
자료구조의 심장: 커밋은 노드(Node), 부모 참조는 방향성 간선(Edge) → DAG 형성
[2]
위상 정렬 (Topological Sort): LOG 출력 시 자식보다 부모가 무조건 먼저 출력되도록 순서 보장
[3]
무방향 BFS (Shortest Path): 다른 브랜치의 두 커밋 간 공통 조상을 경유하는 최단 거리 산출
[4]
역색인 (Inverted Index): 전수 조사 O(N×M)을 해시맵 O(1)으로 단축시키는 검색 엔진 원리

📌 1. 왜 Git의 커밋 히스토리는 DAG인가?

DAG는 Directed Acyclic Graph (방향성 비순환 그래프)의 약자입니다.

Directed (방향성)

자식 커밋은 자신이 생성될 때의 직전 커밋(부모)을 가리킵니다. 간선의 방향은 항상 자식 → 부모입니다.

Acyclic (비순환)

커밋은 이미 존재하는 과거의 커밋만 부모로 지정할 수 있습니다. 미래의 커밋을 부모로 가질 수 없으므로 순환(Cycle)이 구조적으로 불가능합니다.

🔑 2. 해시(SHA-1)와 충돌(Collision) 방어 전략 Hex 6자리

실제 Git은 커밋 내용(메시지 + 작성자 + 타임스탬프 + 부모 해시)을 SHA-1으로 암호화 해싱합니다. 본 Mini Git은 사용성을 위해 앞 6자리를 잘라 쓰되, 비둘기집 원리에 의한 6자리 충돌 발생 시 내부 접미사 카운터(`_1`, `_2`)를 부여하여 세션 내 유일성을 100% 보장합니다.

인터랙티브 DAG 생성기 커밋: 3개
[a1b2c3] Root commit
Author: Alice | 2026-08-31 21:00
parents: []
▲ parent reference
[d4e5f6] Add feature A
Author: Bob | 2026-08-31 21:05
parents: [a1b2c3]
▲ parent reference
[g7h8i9] HEAD (main)
Author: Alice | 2026-08-31 21:10
parents: [d4e5f6]
🎯 Kahn's Algorithm: "부모가 항상 먼저 출력되는 LOG" 시간복잡도: O(V + E)

과제 필수 제약: "학습 목적상 최신순 나열이 아니라, 부모 커밋이 항상 자식 커밋보다 먼저 출력되도록 출력한다."

1 진입차수(In-degree) 계산

간선 방향이 자식 → 부모일 때, 부모 노드의 진입차수는 자신을 부모로 참조하는 자식 커밋의 개수가 됩니다.

2 Queue 기반 탐색

진입차수가 0인 노드(자식이 없는 말단 커밋)를 큐에 넣고, 꺼내면서 부모들의 진입차수를 1씩 감소시킵니다. 차수가 0이 된 부모를 큐에 추가합니다.

3 결과 역순 반환

말단(자식)부터 수집된 결과를 뒤집으면(Reverse) 완벽한 뿌리(Root) 부모 → 자식 커밋 순서의 위상 정렬이 완성됩니다.

💡 피어리뷰 핵심 방어 논리: 왜 재귀 DFS가 아니라 Kahn 알고리즘인가?

"Kahn 알고리즘은 반복문과 큐(deque) 기반이라 파이썬의 재귀 깊이 제한(`RecursionError`, 기본 1,000회)에 완전히 안전하며, 모든 노드를 순회한 후 방문 수가 전체 정점 수보다 적으면 사이클(Cycle)의 존재를 즉시 감지할 수 있는 강력한 무결성 보증이 있습니다."

🌐 PATH: BFS 무방향 최단경로 O(V + E)

두 커밋 간의 거리를 잴 때 "커밋-부모 연결을 무방향(Undirected) 간선으로 간주"합니다.

왜 무방향 간선이어야 하는가?

서로 다른 브랜치에 있는 커밋 feature_commit과 main_commit은 공통 조상 root를 거쳐 연결됩니다 (feature → root → main). 단방향(부모)만 허용하면 자식으로 내려갈 수 없어 두 브랜치 간 경로를 전혀 찾을 수 없습니다.

✓ 동점 처리(Tie-breaking): 최단 경로가 여러 개일 경우, 경로 문자열(hash1->hash2)의 사전순(lexicographical)으로 가장 작은 것을 선택합니다.
🌳 ANCESTORS: DFS 모든 조상 탐색 O(V + E)

해당 커밋에서 도달 가능한 모든 과거 조상 노드를 빠짐없이 수집합니다.

머지 커밋(Merge Commit) 처리의 핵심

머지 커밋은 parents = [hash1, hash2]처럼 부모가 2개 이상입니다. DFS 스택과 visited 집합을 사용하여 여러 갈래로 뻗어나가는 과거 계통을 중복 없이 안전하게 순회합니다.

✓ 스택(Stack) 기반 탐색: 깊이 우선으로 부모 체인을 타고 올라가며 분기된 히스토리 전체를 복원합니다.
⚡ SEARCH: 역색인(Inverted Index) 공간-시간 트레이드오프

모든 커밋을 순회하는 선형 탐색($O(N imes M)$) 대신, 키워드/작성자를 Key로 하고 커밋 해시 집합(set)을 Value로 가지는 역색인을 구축하여 $O(1)$ 즉시 조회를 지원합니다.

순회 검색 (Linear)
매번 10만 개 커밋 전수 검사 → O(N×M) 지연
역색인 (Inverted)
해시맵 key 즉시 조회 → 결과 K개 반환 O(K)

인덱스 갱신 시점: COMMIT 생성 즉시 메시지를 소문자 토큰화하여 keyword_index와 author_index에 등록합니다.

Q1. LOG의 위상 정렬 구현 방식 Kahn vs DFS

"LOG의 부모 먼저 출력 순서는 DFS 재귀로 하셨나요, 아니면 Kahn's 진입차수로 푸셨나요?"

💬 나의 답변: 파이썬 재귀 한계(`RecursionError`)를 원천 차단하고 그래프 사이클 존재를 안전하게 감지하기 위해 반복문 기반 큐를 쓰는 Kahn's Algorithm을 선택했습니다.
Q2. PATH에서 간선 방향 처리 무방향 BFS

"서로 다른 두 브랜치 사이의 최단 경로를 찾을 때 간선을 무방향으로 처리하셨나요?"

💬 나의 답변: 다른 브랜치 커밋끼리는 공통 조상으로 올라갔다가 다시 자식으로 내려와야 하므로 무방향 간선 인접 리스트가 필수적이며, 동점 시 사전순 정렬을 추가했습니다.
Q3. 정렬 알고리즘의 안정성 (Stability) Merge Sort

"표준 sort()가 금지되어 정렬을 직접 만드실 때 안정 정렬(Stable Sort)을 고려하셨나요?"

💬 나의 답변: 동일 작성자/날짜일 때 기존 커밋 생성 순서가 뒤집히지 않도록 보장하기 위해 머지 정렬(Merge Sort)을 기본 알고리즘으로 채택했습니다.
Q4. 역색인 갱신 시점과 트레이드오프 Inverted Index

"SEARCH의 역색인은 검색할 때 만드셨나요, 아니면 커밋할 때 즉시 갱신하셨나요?"

💬 나의 답변: `COMMIT` 생성 시점에 소문자 토큰화하여 `set`에 즉시 등록함으로써, 쓰기 시점의 미세한 비용으로 읽기 속도 $O(1)$을 달성하는 공간-시간 트레이드오프를 취했습니다.
Q5. 해시 충돌(Collision) 방어 메커니즘 Short Hash Collision

"6자리 short hash를 쓸 때 발생할 수 있는 비둘기집 원리의 해시 충돌을 어떻게 방지하셨나요?"

💬 나의 답변: SHA-1 6자리 중복 발생 시 해시맵 충돌을 감지하여 `a1b2c3_1` 형태의 접미사 카운터를 붙여 세션 내 100% 유일성을 방어했습니다.
Q1. 커밋 수가 100만 개로 10배~100배 증가한다면 어디가 가장 먼저 병목이 될까?

1. 메모리(RAM) 병목: 모든 커밋 객체와 역색인 집합이 메모리에 상주 → 디스크 기반 B-Tree/LSM-Tree 인덱스(SQLite 등) 도입 및 노드 Lazy Loading 필요.

2. 전체 위상 정렬 비용: 매 LOG마다 전체 그래프를 위상 정렬하는 비용 부담 → 페이지네이션(`git log -n 20`) 및 부모 링크 기반 온디맨드 스트리밍 이터레이터 적용.

Q2. 만약 PATH 간선을 "부모 방향만 허용(단방향)"으로 바꾸면 어떻게 될까?

• 결과 변화: 오직 직계 조상-자손 관계 사이의 경로만 탐색 가능하며, 서로 갈라진 병렬 브랜치 간의 경로는 No path가 됩니다.

• 구현 수정: 인접 리스트 구축 시 parent → child 역방향 간선 등록 코드를 제거하고 단방향만 탐색하도록 수정합니다.

Q3. `LOG --sort-by=author`에서 "부모-자식 선후 관계"까지 동시에 유지해야 한다면?

• 해결 전략: 단순 작성자 이름 정렬 대신, Kahn 위상 정렬의 큐(Queue)를 작성자 이름 기준 우선순위 큐(Priority Queue / Min-Heap)로 교체합니다.
