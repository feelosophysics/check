## 1. 병합이 없으면 어려운 경우가 생기지 않는다

친구 CLI에는 `MERGE`가 없어서 모든 커밋의 부모가 0개 또는 1개다. 이 그래프를 무방향으로 보면 **트리(또는 트리 여러 개)**이고, 트리에서는 두 점을 잇는 경로가 하나뿐이다. 그래서:

- PATH의 “최단 경로가 여러 개면 사전순” 규칙은 CLI로는 **한 번도 실행될 수 없다.** 친구는 [`shortest_path()`](https://github.com/CMS-SUDO7/CODY-B3-2/blob/4179bb94d536c7f0d24b1c6a2e8b426b1335bddd/algorithms.py#L75)에 이 규칙을 정확히 구현했지만(아래 2절), 확인할 방법이 없다.
- ANCESTORS의 `visited`(병합 뒤 공통 조상 중복 방지)와 LOG의 “부모가 여럿인 커밋 기다리기”도 마찬가지다.

나는 MERGE로 다이아몬드 모양 그래프를 만들 수 있고, [`test_path_string_order_against_all_shortest_paths`](https://github.com/feelosophysics/codsaid/blob/5b0678a5d72b385d4b7095bf92797f6d20263ee8/01_Basic/b5-2/tests/test_minigit.py#L261)가 4노드 DAG 64개의 모든 출발·도착 조합을 독립적으로 열거한 답과 비교한다.

친구 README에는 “서로 다른 작성자는 모델 데이터로 별도 검증했습니다”라고 적혀 있지만, 저장소에 그 검증 코드가 없다. 다른 사람은 다시 확인할 수 없다.

**이야기할 질문:** 과제 범위에서 생기지 않는 경우를 구현했다면 어떻게 증명할까? 모델 함수를 직접 부르는 작은 테스트(부모 2개짜리 `Commit`을 손으로 만들기)면 충분할까? 작성자를 바꿀 수 없는데 `LOG --sort-by=author`를 어떻게 보여 줄까 — 나처럼 명령을 더할까, 테스트로만 보일까?

## 2. 최단 경로 동률: 두 가지 방법

요구사항은 “경로를 `hash1->hash2->...` 문자열로 만들었을 때 사전순이 가장 작은 경로”다.

- **친구:** 도착점에서 BFS를 한 번 돌려 모든 커밋까지의 거리를 구한 뒤, 출발점부터 “거리가 1 줄어드는 이웃 중 가장 작은 것”을 골라 걷는다. 비교할 때 `neighbor + "->"`를 쓰는 덕분에 한 hash가 다른 hash의 접두사여도 올바르다.
- **나:** 출발점에서 BFS를 돌리며 이웃을 `hash + "->"` 기준으로 머지 정렬해 방문하고, 처음 발견한 경로를 쓴다.

둘 다 맞는 방법이고, “`->`를 붙여 비교한다”는 같은 함정을 같은 방식으로 피했다. 차이는 비용과 설명 난이도다. 친구 방식은 정렬이 없고 왜 맞는지 설명하기 쉽다(각 단계에서 최솟값 하나만 고르면 된다). 내 방식은 도착점을 찾으면 바로 멈추지만 매 커밋마다 이웃을 정렬한다. “정렬된 순서로 BFS하면 처음 찾은 경로가 사전순 최소”라는 성질은 직관적이지 않아 위 전수 테스트로 확인했다.

**이야기할 질문:** 각자 자기 방법이 맞는 이유를 말로 설명해 보자. 친구 방식에서 도착점부터 BFS하는 이유는? 내 방식에서 큐에 넣을 때 방문 표시를 하지 않으면 무엇이 틀어질까?

## 3. 그래프 표를 언제 만드는가

친구는 [`commit()`](https://github.com/CMS-SUDO7/CODY-B3-2/blob/4179bb94d536c7f0d24b1c6a2e8b426b1335bddd/repository.py#L77)에서 `children`(부모→자식)과 `neighbors`(무방향)를 같이 갱신한다. LOG와 PATH는 이미 만들어진 표를 쓰므로 조회마다 표를 다시 만들지 않는다. 대신 같은 사실(부모 관계)이 세 군데(`Commit.parents`, `children`, `neighbors`)에 저장되므로, 커밋을 만드는 경로가 늘어나면(예: MERGE 추가) 세 곳을 함께 고쳐야 한다.

나는 [`graph.py`](https://github.com/feelosophysics/codsaid/blob/5b0678a5d72b385d4b7095bf92797f6d20263ee8/01_Basic/b5-2/minigit/graph.py)에서 매번 `parents`만 보고 표를 만든다. 원본이 하나라 어긋날 일은 없지만, LOG·PATH 한 번마다 O(V+E)가 든다. 학습용 규모에서는 둘 다 체감 차이가 없다.

친구의 `Commit`은 `frozen=True`와 튜플 `parents`로 **생성 후 바꿀 수 없다.** “새 커밋은 이미 있는 커밋만 부모로 삼고, 기존 커밋의 부모는 바뀌지 않는다 → 순환이 생길 수 없다”는 DAG 논리를 코드가 보장하는 셈이다. 나는 같은 의도로 `parents[:]` 복사만 하므로, 다른 코드가 `commit.parents.append(...)`를 하면 막을 수 없다.

**이야기할 질문:** 같은 정보를 여러 곳에 두는 대가는? MERGE를 친구 구조에 더하면 어디를 고쳐야 할까? 나는 `Commit`을 `frozen` dataclass로 바꿀 이유가 있을까?

## 4. 오류와 결과는 어떤 모양으로 돌려주는가

| | 친구 | 나 |
| --- | --- | --- |
| 모델의 성공 결과 | `Commit` 객체·목록 | 화면 문구 문자열 (`[main a1b2c3-1] ...`) |
| 모델의 실패 | `ValueError("Unknown branch: x")` | 오류 문구 문자열 |
| CLI | 결과를 바로 `print` | 출력할 문자열을 반환, `run()`이 출력 |

친구 구조는 **모델이 화면 문구를 모른다.** 다른 화면(웹, GUI)을 붙여도 `Repository`를 그대로 쓸 수 있다. 다만 `execute()`가 직접 `print`하므로 CLI를 테스트하려면 표준 출력을 가로채야 하고, 사용자 오류와 코드 버그가 모두 `ValueError`라 구분되지 않는다. REPL은 `ValueError`만 잡으므로, 그 밖의 예외가 나면 프로그램이 끝나고 **메모리에 있던 저장소가 통째로 사라진다.**

내 구조는 `execute()`가 문자열을 돌려줘 테스트하기 쉽다. 하지만 모델이 화면 문구를 만들고, 성공과 실패가 같은 `str`이라 **호출한 쪽이 결과만 보고 실패를 구분할 수 없다.** 테스트도 문구에 묶여 문구를 바꾸면 깨진다.

**이야기할 질문:** 오류 전용 예외 클래스(`MiniGitError`)를 두면 두 구조의 단점이 어떻게 줄까? 모델·CLI·출력의 경계를 어디에 그을까?

## 5. 같은 요구사항, 다른 해석

과제 문서가 정하지 않은 부분에서 서로 다르게 골랐다. 어느 쪽이 정답이라기보다, **선택과 이유를 README에 적었는지**가 중요하다. 둘 다 대부분 적었다.

| 항목 | 친구 | 나 | 생각할 점 |
| --- | --- | --- | --- |
| 다시 `INIT` | 거부 | 초기화 | 확인 없이 모든 커밋을 지우는 명령이 괜찮을까? |
| `SEARCH "add login"` | 두 단어가 다 있으면 일치 | 붙어 있어야 일치 | 사용자가 기대하는 것은? AND는 역색인 교집합만으로 끝나고, 구절은 후보 메시지를 다시 읽어야 한다 |
| 작성자 비교 | `Alice` ≠ `alice`, 정렬은 대문자가 먼저 | 대소문자 무시 | 키워드는 소문자로 바꾸면서 작성자는 그대로인 것이 일관적일까? |
| 인자 공백 | 메시지·이름 양끝 공백 유지 | `strip()` | `INIT " Alice "` 뒤 `SEARCH --author=Alice`가 실패한다 |
| 역슬래시 | `shlex` 기본값이라 따옴표 밖 `\`가 사라짐 | 이스케이프를 끔(DIFF의 Windows 경로용) | 대신 나는 `"say \"hi\""`처럼 따옴표를 이스케이프할 수 없다 |
| Ctrl+C | 프로그램 종료 | 입력 줄만 취소 | 메모리 저장소에서 실수로 누르면? |
| 검색 결과 순서 | 생성 순서(목록 색인) | 시각·hash로 머지 정렬(집합 색인) | 색인에 목록과 집합 중 무엇을 쓸지가 순서까지 정한다 |

**hash 설계**도 흥미롭다. 친구의 순수 카운터는 같은 명령을 다시 치면 같은 hash가 나와 README 예제(`PATH 00000002 00000003`)를 그대로 따라 할 수 있다. 내 hash는 SHA-1 앞부분을 붙여 Git처럼 보이지만, 유일성은 뒤의 번호가 보장하므로 앞부분은 장식에 가깝고, README 예제의 ID를 그대로 칠 수 없다.

**시각:** 친구는 UTC로 저장하고 UTC로 보여 줘, 한국에서 쓰면 출력 시각이 9시간 느리게 보인다. 나는 시간대 없는 숫자로 저장하고 지역 시각으로 보여 준다. 흔한 원칙은 “UTC로 저장, 지역 시각으로 표시”다.

## 6. 과제 형식과 문서

- **실행 방법:** 과제는 엔트리 포인트 하나(예: `main.py`)와 `python main.py` 실행을 예로 든다. 친구는 그대로 따랐고, 나는 `python -m minigit`이라 `main.py`가 없다. 채점자가 `python main.py`부터 칠 가능성을 생각하면 한 줄짜리 `main.py`를 두는 편이 안전하다.
- **README 경로:** 친구 README의 `cd B3-2-mini-git`은 저장소 이름(`CODY-B3-2`)과 다르다.
- **과제 원문:** 친구 저장소는 공개 상태로 미션 PDF를 포함한다. 과정 자료를 공개 저장소에 올려도 되는지 규정을 확인해 볼 만하다. 나는 원문을 저장소에 넣지 않았다.
- **학습 문서:** 친구의 [그림·시각화 해설](https://github.com/CMS-SUDO7/CODY-B3-2/blob/4179bb94d536c7f0d24b1c6a2e8b426b1335bddd/docs/algorithm_visual_guide.md)은 병합 정렬·역색인·Kahn 알고리즘을 직접 조작해 볼 수 있어 복습용으로 좋다. 나는 명령을 실행하며 코드와 상태를 연결하는 [실습 가이드](https://github.com/feelosophysics/codsaid/blob/5b0678a5d72b385d4b7095bf92797f6d20263ee8/01_Basic/b5-2/study/study_guide.md)가 중심이다.
