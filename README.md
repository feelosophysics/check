# B2-1 가계부, 같이 읽고 이야기하기

같은 파일 기반 콘솔 가계부를 만들었지만, 오류 처리 정책과 데이터를 연결하는 방식에서 차이가 난다. **같은 상황에서 왜 다른 결과가 나오는지**를 중심으로 비교했다.

비교 기준은 2026-10-21의 [NiceTry3675/B2-1 (`cdc1a95`)](https://github.com/NiceTry3675/B2-1/tree/cdc1a955b34f1f62a765a01718e664827d8fc5aa)와 [feelosophysics/codsaid의 Basic B2-1 (`7d1bb85`)](https://github.com/feelosophysics/codsaid/tree/7d1bb85bbc496e91d07e0d03aae8eae14f8567a4/01_Basic/b2-1)이다. 아래의 ‘친구’와 ‘내 구현’은 각각 이 코드를 가리킨다.

## 먼저 보는 공통점과 차이

둘 다 표준 라이브러리로 JSONL 파일에 거래를 저장하고, CLI·서비스·저장소·모델을 나눈다. 파일 읽기에는 제너레이터를, 공통 처리에는 데코레이터를 사용한다. 거래 CRUD, 검색, 월별 집계, 예산, CSV, 백업, 반복 거래까지 구현했다.

| 관점 | 친구 구현 | 내 구현 |
| --- | --- | --- |
| 기능 배치 | 거래·카테고리·예산 서비스와 CSV·백업·반복 거래를 나눔 | `BudgetService` 한 곳에서 주요 기능을 이어 읽을 수 있음 |
| 데이터 표현 | 불변 dataclass, 날짜·월 전용 타입, 거래 종류 Enum | 수정 가능한 dataclass, 문자열 날짜·종류, 리스트 태그 |
| 거래 수정 | `update --id … --amount …`처럼 옵션으로 전달 | 질문을 따라 입력하는 대화형 방식 |
| CSV 오류 | 기본은 전체 취소, `--skip-invalid`로 정상 행만 저장 | 정상 행을 저장하고 오류 행과 사유를 반환 |
| 반복 거래 표시 | 전용 `recurring_id` 필드 | 일반 태그에 `REC-000001` 같은 표시를 넣음 |
| 백업 | 생성·목록·복원, 복원 직전 자동 백업 | JSONL 파일을 ZIP으로 만드는 기능 |

내 구현은 기능이 한 서비스에 모여 있어 호출 흐름을 따라가기 쉽다. 친구 구현은 각 기능의 경계를 더 세분화해 따로 검증하거나 바꾸기 편하다. 대신 처음 읽을 때 따라가야 할 타입과 파일도 늘어난다. **분리가 필요한 이유를 설명할 수 있는가**가 파일 수보다 좋은 비교 기준이다.

## 같은 상황을 넣어 보면

다음 네 사례는 임시 데이터로 직접 확인한 결과다. 카테고리 이름은 각 프로그램에 등록된 값을 사용했다.

| 상황 | 친구 구현 | 내 구현 | 함께 볼 의미 |
| --- | --- | --- | --- |
| 정상 금액 100원 한 행 + 금액 -1원 한 행을 기본 설정으로 CSV 가져오기 | 오류를 알리고 거래 0건 추가 | 1건 추가, 1건 건너뜀 | 전체 취소와 부분 성공 중 어떤 정책이 사용자에게 맞을까? |
| 거래 두 건 추가 → 두 번째 삭제 → 새 거래 추가 | ID `1 → 2 → 3` | ID `TX-000001 → TX-000002 → TX-000002` | ‘현재 데이터에서 중복 없음’과 ‘삭제한 번호도 재사용하지 않음’은 다른 조건이다. |
| 거래는 없고 반복 규칙만 사용하는 카테고리 삭제 | 삭제 차단. 대체 분류를 주면 규칙도 이관 | 삭제 허용. 규칙은 예전 분류를 유지하고, 이후 그 분류로 거래까지 생성 | 연결된 데이터에는 기존 거래뿐 아니라 미래 거래의 규칙도 포함된다. |
| 거래 JSONL 끝에 `BROKEN` 한 줄을 붙이고 조회 | 경고 후 정상 거래 조회 | `JSONDecodeError` 발생 | 손상된 줄을 만났을 때 계속 읽을지, 멈출지 결정해야 한다. |

CSV의 기본 정책은 서로 다른 선택이다. 내 구현의 부분 성공은 정상 자료를 바로 살릴 수 있지만, 오류를 고친 CSV 전체를 다시 넣으면 이미 저장한 거래가 중복될 수 있다. 친구의 전체 취소는 재시도 범위가 명확하지만 정상 행도 다시 처리해야 한다. 친구 코드에는 부분 성공을 고르는 옵션과 저장 전 확인하는 `--dry-run`도 있다. 두 구현 모두 같은 CSV를 다시 가져오는 것 자체를 자동으로 중복 제거하지는 않는다.

ID 재사용은 현재 살아 있는 거래끼리 곧바로 충돌한다는 뜻은 아니다. 다만 삭제한 거래의 ID를 메모나 다른 자료에서 참조하고 있었다면 새 거래와 혼동할 수 있다. 친구는 `meta.jsonl`에 발급 기록을 따로 두고, 내 코드는 현재 거래의 최댓값에 1을 더한다.

카테고리 삭제는 내 구현에서 먼저 보완할 만한 부분이다. 기존 거래 이관은 이미 처리하지만 반복 규칙은 검사하지 않는다. 규칙도 확인해 삭제를 막거나 함께 옮기고, 반복 거래 생성 직전에도 카테고리가 존재하는지 검사하면 연결을 지킬 수 있다.

## 제너레이터와 원자적 쓰기는 어디까지 효과가 있을까?

**`yield`로 반환한다고 처리 전체가 적은 메모리를 쓰는 것은 아니다.** 내 `list_transactions()`는 먼저 모든 거래를 리스트로 읽고 정렬한 다음 하나씩 반환한다. 친구의 최신 N건 조회는 `heapq.nlargest`로 후보 N건을 유지한다. 두 방법 모두 파일 전체를 읽지만, 거래가 많고 N이 작을 때 메모리 사용량은 달라진다. 친구도 개수 제한 없는 전체 정렬과 CSV 내보내기에서는 결과를 메모리에 모은다.

월별 합계는 내 코드에서도 한 건씩 읽어 누적한다. 따라서 ‘내 코드는 전부 리스트 처리, 친구 코드는 전부 스트리밍’이라고 나누면 틀린 비교다. **읽기 → 필터 → 정렬 → 출력 중 어느 단계가 데이터를 모으는지**를 각각 보면 된다.

**임시 파일을 교체하는 것과 모든 장애에서 데이터를 보장하는 것도 다르다.** 둘 다 수정·삭제 시 임시 파일을 쓰고 `os.replace()`로 교체한다. 내 코드는 새 내용을 리스트로 모으고 고정된 `.tmp` 이름을 쓴다. 친구는 줄 단위 재작성, 고유 임시 이름, `flush`·`fsync`, 손상된 줄 보존까지 다룬다. 내 구현을 읽을 때는 기본 원리를, 친구 구현을 읽을 때는 실패 시 처리까지 확장해 볼 수 있다.

단, 파일 하나의 교체가 원자적이라고 여러 파일을 바꾸는 작업 전체나 여러 프로세스의 동시 실행까지 안전해지는 것은 아니다. 친구의 손상 줄 건너뛰기도 조회를 계속하게 해 주지만, 그 결과의 합계는 빠진 거래가 있는 부분 합계일 수 있다. 경고를 사용자에게 어떻게 보여 줄지도 같이 생각할 문제다.

## 같이 이야기해 볼 질문

1. **CSV 기본값은 무엇이 좋을까?** 오류 한 행 때문에 전부 취소하는 것과 정상 행부터 저장하는 것 중, 사용자가 재시도할 때 덜 헷갈리는 쪽은 무엇일까?
2. **반복 거래의 표시를 일반 태그로 두어도 될까?** 사용자가 표시 태그를 지우거나 우연히 같은 태그를 넣으면 중복 판정에 어떤 일이 생길까? 전용 필드의 비용은 얼마나 될까?
3. **어느 정도까지 나누면 읽기 편할까?** 내 서비스에서 CSV만 먼저 분리한다면 무엇이 쉬워질까? 친구 구조에서 `add` 한 건이 저장되기까지 각 객체가 필요한 이유를 설명할 수 있을까?
4. **안전하다는 말의 범위는 어디까지일까?** 정상 실행, 입력 오류, 쓰기 실패, 강제 중단, 동시 실행을 나누면 지금 각 코드가 다루는 범위는 어디일까?

## 짧게 같이 해볼 것

먼저 내 코드에서 **반복 규칙만 연결된 카테고리의 삭제를 막는 작은 수정**을 해 보면 좋겠다. 그다음 대체 카테고리를 주었을 때 기존 거래와 반복 규칙을 함께 옮기도록 확장한다. 친구의 `CategoryService.remove()`와 나란히 보면 검사 대상과 처리 순서가 왜 필요한지 드러난다.

여유가 있으면 같은 CSV를 두 번 가져오고, 반복 거래의 표시 태그를 바꾼 뒤 같은 달에 다시 생성해 보자. 기능을 더 붙이기 전에 **다시 실행해도 기대한 결과인지**를 확인하는 연습이 된다.
