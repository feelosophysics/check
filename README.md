## 1. 상태와 화면이 어긋날 수 있는 길이 있는가?

친구는 Projects 상태를 `setProjectsState({ ... })`로만 바꾸고, 이 함수가 매번 `renderProjects()`를 부른다. 필터 버튼의 `active`·`aria-pressed`도 렌더 함수가 상태를 보고 다시 그린다. 그래서 상태만 바뀌고 화면이 그대로 남는 실수가 구조적으로 생기기 어렵다.

내 코드는 `STATE.portfolio.filter = ...`처럼 직접 대입한 뒤 `renderProjectsUI()`를 따로 부른다. 지금은 빠짐없이 호출하지만, 호출을 하나 빠뜨려도 막아 주는 장치는 없다. 또 필터 버튼의 `active` 클래스는 렌더 함수 밖에서 `classList`로 직접 바꾼다. **화면 일부가 상태가 아닌 곳에서 관리되는 셈이다.**

필터 버튼을 만드는 방식도 다르다. 친구는 받은 데이터에서 버튼을 만들기 때문에 “버튼은 있는데 결과가 0개”인 경우가 생기지 않는다. 내 버튼은 HTML에 고정돼 있어, 해당 언어 저장소가 없으면 빈 상태 문구가 뜨고 `language`가 `null`인 저장소(`Others`)는 따로 고를 수 없다.

**이야기할 질문:** 상태를 바꾸는 함수를 하나로 모으는 장점과 비용은? “저장소가 0개”와 “필터 결과가 0개”는 같은 문구로 보여도 될까? 필터 목록은 데이터에서 만들어야 할까, 보여 주고 싶은 언어를 직접 정해야 할까?

## 2. 외부 데이터를 `innerHTML`에 넣을 때

GitHub 저장소 설명은 저장소 주인이 마음대로 쓰는 텍스트다. 내 코드는 `${repo.name}`, `${description}`을 그대로 템플릿에 넣는다. 설명에 `<img src=x onerror=...>` 같은 문자열이 있으면 태그로 해석되어 스크립트가 실행될 수 있다. 지금은 내 저장소만 불러오므로 위험이 작지만, 같은 패턴을 다른 사람의 데이터에 쓰면 문제가 된다.

친구는 `escapeHTML()`로 `& < > " '`를 바꾼 뒤 넣는다. 친구 페이지는 `?user=아이디`로 **다른 계정의 저장소도 불러올 수 있으므로** 이 처리가 실제로 필요한 구조다. 다만 이스케이프는 `href`에 `javascript:` 같은 주소가 들어오는 문제까지 막지는 않는다. 지금은 GitHub가 주는 `html_url`만 쓰므로 괜찮지만, 규칙으로 기억해 둘 만하다.

**이야기할 질문:** 문자열을 이스케이프해 `innerHTML`로 넣는 방식과 `createElement` + `textContent`로 만드는 방식 중 무엇이 읽기 쉽고 안전할까? React의 JSX는 이 문제를 어떻게 처리할까?

## 3. 스크롤 애니메이션: 임계값과 “JS가 안 돌 때”

Intersection Observer의 `threshold`는 **요소 자신의 넓이 중 몇 %가 보이는지**를 기준으로 한다. 그래서 요소 높이가 `화면 높이 ÷ threshold`보다 크면 비율에 끝내 도달하지 못해 애니메이션이 실행되지 않는다.

- 친구(`0.2`): 화면 5배보다 큰 요소만 문제. 그래도 카드가 많은 Projects 그리드는 일부러 관찰 대상에서 뺐다고 README에 이유를 적었다.
- 나(`0.5`): 화면 2배보다 큰 요소는 투명한 채로 남는다. 지금 관찰하는 카드·폼 크기에서는 괜찮아 보이지만, 콘텐츠가 길어지면 문제가 될 수 있는 값이다.

반대로 **JS가 실행되지 않을 때**는 내 구조가 안전하다. 친구는 HTML에 `.reveal`(처음에 `opacity: 0`)을 적어 두어, 스크립트가 실패하면 About·Skills·Contact가 보이지 않는다. 나는 JS가 `.fade-in`을 붙이므로 스크립트가 실패해도 본문은 그대로 보인다.

둘 다 `prefers-reduced-motion`(움직임 줄이기 설정)은 처리하지 않았다. 타이핑 효과와 등장 애니메이션 모두 해당한다.

**이야기할 질문:** threshold는 어떤 기준으로 정할까? 애니메이션처럼 없어도 되는 기능이 실패할 때 본문까지 사라지지 않게 하려면? 움직임 줄이기 설정을 켠 사용자에게는 무엇을 보여 줄까?

## 4. 키보드와 스크린 리더로도 쓸 수 있는가?

| 항목 | 친구 | 나 |
| --- | --- | --- |
| 햄버거 메뉴 | `<button>` + `aria-expanded`·`aria-controls`, 상태에 따라 라벨 변경 | `<div>`라서 Tab으로 갈 수 없고 Enter로 열 수 없음 |
| 맨 위로 | `<button>` | `<a href="#">` + `preventDefault()` |
| 타이핑 제목 | 문장을 HTML에 적어 두고 JS가 지웠다가 다시 씀 | `<h1>`을 비워 두고 문장은 JS에만 있음 |
| 프로젝트 목록 | `aria-live="polite"`로 목록 변경을 알림 | 별도 알림 없음 |

내 `<h1>`은 HTML만 보면 비어 있다. JS가 실패하거나 HTML을 먼저 읽는 검색 엔진·도구는 제목을 볼 수 없다. 친구 방식은 이 문제가 없지만, 타이핑 중에는 제목 내용이 계속 바뀐다. 완성된 문장을 스크린 리더에 한 번만 전달하는 방법도 생각해 볼 수 있다.

## 5. 실패를 어떻게 구분하고, 한 실패가 어디까지 번지는가?

**API 실패 문구.** 나는 403이면 “API 호출 제한 초과”, 나머지는 모두 “데이터를 불러올 수 없습니다”이고, 네트워크 오류는 브라우저 원문(`Failed to fetch` 등)이 그대로 보인다. 친구는 403·429, 404, 그 밖의 HTTP 오류, 네트워크 오류(`TypeError`)를 나눈다. 다만 확인할 점이 두 가지 있다.

- `TypeError`는 네트워크뿐 아니라 코드 실수에서도 난다. 예를 들어 응답이 배열이 아니어서 `data.filter`가 실패해도 “네트워크 연결을 확인해 주세요”로 보인다.
- GitHub의 403이 모두 요청 한도 초과는 아니다. 남은 호출 수는 응답 헤더 `X-RateLimit-Remaining`으로 확인할 수 있다.

**목록 개수.** 나는 `per_page`를 지정하지 않아 기본 30개까지만 받는다. 지금 공개 저장소가 3개라 문제가 없지만, 친구는 44개라 `per_page=100`이 필요했다. 100개를 넘으면 둘 다 페이지를 나눠 받아야 한다.

**한 실패의 범위.** 내 `main.js`는 첫 줄에서 `localStorage.getItem()`을 예외 처리 없이 부른다. 저장소 접근이 막힌 환경에서 여기서 오류가 나면 **같은 파일의 메뉴·스크롤·API·폼이 전부 실행되지 않는다.** 친구는 `try/catch`로 감쌌고, 파일도 나뉘어 있어 한 파일의 오류가 다른 기능까지 멈추지 않는다. 파일 분리는 “찾기 쉬움”뿐 아니라 **실패의 범위를 나누는 효과**도 있다.

**첫 화면 깜빡임.** 둘 다 `defer` 스크립트에서 `data-theme`을 정하므로, 다크 모드 사용자는 HTML이 다 그려진 뒤 테마가 바뀌는 순간 밝은 화면을 잠깐 볼 수 있다.

**이야기할 질문:** 사용자에게는 어느 정도까지 원인을 구분해 보여 줄까? 기능을 파일로 나눌 때 무엇을 기준으로 할까? 테마 깜빡임을 없애려면 `<head>`에 작은 스크립트를 두어야 하는데, 과제 규칙과 충돌하지 않을까?

## 6. 폼: 언제 오류를 보여 주고, 실제로 보내는가?

친구는 `input` 이벤트마다 검증한다. 고치는 즉시 오류가 사라져 좋지만, 이메일을 치는 도중에도 “형식이 올바르지 않습니다”가 먼저 보인다. 나는 README에 적은 대로 **처음 제출하기 전에는 오류를 보여 주지 않고**, 입력 중에는 오류를 지우기만 한다. 대신 제출 후 다시 틀리게 바꾸면 다음 제출 때까지 알 수 없다.

친구는 검증용 객체(`validators`)와 오류 상태(`formErrors`)를 따로 두어 필드가 늘어도 한 줄로 처리한다. 나는 필드마다 `if`와 리스너를 따로 썼고, 오류 표시를 `style.display`로 바꾼다. 친구는 `classList`만 쓴다.

실제 전송은 나만 구현했다. Formspree에 보내고 실패하면 `alert`를 띄운다. 다만 응답을 기다리는 동안 보내기 버튼이 그대로 눌려 중복 전송될 수 있고, 내 README는 “action URL을 실제 ID로 교체 필요”라고 적혀 있는데 HTML에는 이미 ID가 들어가 있어 문서가 코드와 맞지 않는다.

**이야기할 질문:** 오류를 보여 주는 시점은 입력 중, 칸을 벗어날 때(`blur`), 제출 후 중 언제가 좋을까? 실제 전송을 붙이면 로딩·중복 클릭·실패를 화면에서 어떻게 보여 줄까?

## 7. “잘 동작한다”를 무엇으로 보여 주는가?

친구의 `scripts/demo.mjs`는 외부 패키지 없이 Node와 Chrome DevTools Protocol만으로 정적 규칙(`var`·`onclick`·인라인 스타일 0건 등)과 실제 클릭·입력·스크롤을 확인한다. GitHub API 응답을 가로채 **로딩·403·네트워크 끊김처럼 일부러 만들기 어려운 상태까지 재현**하는 점이 특히 배울 만하다. 다만 Chrome 기본 경로가 macOS 기준이라 Windows에서는 `CHROME_PATH`를 지정해야 하고, 실제 API를 호출하므로 시간당 호출 한도의 영향을 받는다.

나는 체크리스트와 스크린샷으로 결과를 설명했다. 문서 길이도 다르다. 친구 README는 약 1,200줄로 개념·자료구조·흐름도까지 담았고, 내 README는 약 450줄에 접기 블록으로 설명을 넣었다.

**이야기할 질문:** 평가자나 다음 사람이 가장 빨리 확인하고 싶은 것은 무엇일까? 테스트를 실제 API에 의존하게 할까, 응답을 고정할까? README에 저장소 개수 같은 바뀌는 숫자를 적으면 언제 다시 맞춰야 할까?
