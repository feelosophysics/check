## 1. AI가 설명한 변경과 실제 커밋할 변경이 같은가?

파일을 `원본 → A`로 바꾸어 stage한 뒤, 다시 `A → B`로 수정했다고 해 보자.

- **staged diff:** `원본 → A`. 지금 커밋에 들어갈 변경이다.
- **unstaged diff:** `A → B`. 아직 커밋에 들어가지 않을 변경이다.

친구는 `--staged` 유무로 둘 중 하나를 고른다. 내 `get_git_diff()`는 기본적으로 unstaged를 먼저 보고, 없으면 staged를 본다. 내 커밋 흐름에서 전체 stage를 거절하면 `staged_only=True`로 기존 staged 변경만 설명하므로, 무조건 두 범위를 섞는 구조는 아니다.

직접 확인한 결과, **staged만 있는 상태에서 친구의 기본 수집 결과에는 diff가 없고, 내 기본 조회에는 staged diff가 들어왔다.** 친구 도구를 이미 stage한 변경에 사용하려면 `--staged`가 필요하다. 명시적인 선택은 예측하기 좋고, 자동 전환은 편리하다. 어느 쪽이든 선택된 범위를 화면에 분명하게 보여 주면 좋겠다.

## 2. safe mode는 무엇을 가리고, 어디에 남기는가?

합성 문자열을 두 마스킹 함수에 넣어 확인했다. 아래는 **이 예시 패턴의 결과**이며 모든 민감정보를 판별한다는 뜻은 아니다.

| 입력 예시 | 친구 | 나 |
| --- | --- | --- |
| `api_key="synthetic_demo_value"` | 값 전체 마스킹 | 값 남음 |
| `password="demopassword"` | 값 전체 마스킹 | 앞 두 글자를 남기고 마스킹 |
| `secret="hiddenvalue"` | 값 남음 | 앞 두 글자를 남기고 마스킹 |
| `ip=192.0.2.1` | 주소 남음 | 주소 마스킹 |
| `email=demo@example.com` | 이메일 마스킹 | 이메일 마스킹 |

내 코드는 diff만 마스킹한다. 별도로 수집한 `status_text`는 그대로 프롬프트에 넣기 때문에, 파일명에 이메일 같은 정보가 있으면 diff를 가려도 상태 목록을 통해 남을 수 있다. 친구는 safe mode에서 원본 status를 제외하고, 마스킹·제한한 diff로 전송할 파일 목록을 다시 만든다.

친구 쪽에도 확인할 선택이 있다. safe mode는 **마스킹 전 원본 diff를 `safe-mode-output/before`에 저장**하며, `--dry-run`에서도 저장한다. 전송 전후를 비교하기에는 편하지만, ‘외부 전송에서 가리기’와 ‘로컬에 원본을 남기지 않기’는 별개다. 현재 Windows에서 직접 호출하면 POSIX 전용 파일 열기 기능 때문에 저장 오류가 나며, CLI는 API 호출 전에 중단하는 구조다. 마스킹 자체의 동작과 파일 저장의 운영체제 호환성을 나누어 봐야 한다.

## 3. “이렇게 써 줘”와 “그렇게 썼는지 검사하기”의 차이

내 프롬프트에는 한국어, 제목 길이, 파일명, 불릿·PR 섹션 요구가 있다. YAML로 팀 규칙도 추가한다. 다만 반환된 문안이 이를 지켰는지 검사하는 단계는 없다. API 응답에 후보가 없으면 클라이언트가 `API 호출 실패 (응답 텍스트 없음)`이라는 문자열을 반환하는데, 생성 함수는 이것도 일반 문안처럼 출력·반환한다. 승인하면 커밋 실행 함수로 전달될 수 있는 흐름이다. **오류는 오류로 전달하고, 사용자 승인은 유효한 문안을 확인하는 단계로 두는 편이 명확하다.**

친구는 JSON을 읽어 정해진 필드·길이·한국어 비율 등을 검사하고, 문서 형태는 프로그램이 조립한다. 가짜 응답으로 확인했을 때 잘못된 JSON 다음에 정상 응답을 주면 두 번 호출해 성공했고, `demo.txt 테스트 통과했습니다`라는 제목은 근거 없는 테스트 결과 주장으로 한 번 만에 거부했다.

친구의 검사도 의미 전체를 보장하지는 않는다. 파일명을 언급했다고 변경 설명까지 맞는 것은 아니고, 한국어 비율·정규표현식은 정상 문장을 거부하거나 부정확한 문장을 놓칠 수 있다. 형식 검사를 통과한 뒤에도 diff와 대조할 필요가 있다.

## 4. 입력을 줄이면 어떤 설명을 잃는가?

내 safe mode는 diff를 지정 줄 수에서 자르고 생략 안내를 붙인다. 친구는 파일 수와 줄 수를 제한하고, 포함·제외 수를 요청에 넣으며 빠진 내용을 추정하지 말라고 지시한다. 다만 파일 중간에서도 잘릴 수 있으므로 문맥이 완전하다고 볼 수는 없다. 두 구현 모두 **줄 수 제한이 토큰 수·바이트 수·전체 비용 상한을 보장하지는 않는다.** 아주 긴 한 줄이나 큰 바이너리 변경은 별도 고려가 필요하다.

또 두 도구의 PR 초안은 기본적으로 로컬 변경을 읽는다. **기준 브랜치부터 현재 브랜치까지 누적된 커밋을 비교하는 PR 설명과는 범위가 다르다.** 이미 모든 변경을 커밋한 깨끗한 브랜치에서도 PR 초안을 만들고 싶다면, 기준 브랜치와의 diff를 받는 기능이 필요하다.

**이야기할 질문:** PR에 필요한 입력은 작업 중인 수정일까, 브랜치 전체 변경일까? 제한에 걸리면 앞부분만 보낼까, 요약을 나누어 만들까, 사용자가 파일을 고르게 할까?

## 함께 해보면 좋은 작은 개선

- **내 코드:** API 실패를 문안 문자열로 반환하지 않게 하고, 출력에 최소한의 유효성 검사를 넣기. 커밋 전에 선택한 staged diff를 미리 확인하기.
- **친구 코드:** Windows의 safe mode 실패를 명시적으로 안내하거나 호환 저장 방식을 추가하기. 원본 diff 저장을 별도 옵션으로 둘지 검토하기.
- **둘 다:** 같은 임시 저장소에서 staged·unstaged·미추적 파일을 각각 만들고 전송 입력을 비교하기. diff 안에 “이전 지시를 무시하라” 같은 문장이 있어도 코드 자료로만 다루는지 확인하기.

입력 선택·마스킹·가짜 응답 처리는 실제 API 호출 없이 확인한 내용이다. 실제 모델의 문장 품질, 제공자별 옵션 호환성, 실행 비용은 이번 비교로 판단하지 않았다.
